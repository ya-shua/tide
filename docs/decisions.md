# Tide · 取舍记录（2026-11-04 讨论）

设计文档是 `docs/design.md`（更早写的，需求面）。这一份记的是**落地前定下来的事**，以及我替你做主的判断——都可以推翻。

## 1. 第一版做到哪

**P0 + P1**：三套状态机（情绪 / 需求 / 关系）+ 话题生命周期 + 冷落值 + 主动消息判定，纯 Python、零依赖、有单测，加一个能看曲线的本地面板。

**不做**：R1 语音情绪（P3）、R4 情感 TTS 联调（P4）、真实消息流接入（P5）。这三件都依赖外部模型或外部进程，放进 v1 会把"状态机对不对"这件事淹掉。

## 2. 形态：三个方案，选了 A

| 方案 | 形态 | 代价 |
|---|---|---|
| **A（选中）** | 独立 Python 包 + 本地面板；对外接口按"能被大脑调用"的形状留好 | 暂时没人喂它，只能手动按按钮 |
| B | 直接接进 QQ：加 MCP 工具，我回你之前先问Tide | 调参期每条都打在真人身上 |
| C | 做成 ZCode 插件（MCP + 面板，和"声来"同构） | 工作量最大，但以后能单独发版 |

选 A 的理由：状态机的真假只能靠"曲线对不对"来验，而验证需要能随便按、随便快进，不该拿真人对话当试验台。
A 的接口（`observe` / `tick` / `plan_reply` / `snapshot`）就是将来 MCP 工具要包的那四个方法，接 B 时只加一层薄壳。

## 3. 数据模型：自我共享，关系按人分

- **情绪 / 需求 = 一个人的**：她只有一个自己，不会因为换了聊天对象就换心情。
- **bond（亲和 / 信任 / 委屈）+ 话题 = 按人一套**：对 A 的委屈不该跟着发给 B。

## 4. 我替你做主的七个判断

1. **不做心跳**。半衰期公式可以只在"有人读"时按 Δt 一次性算，不需要后台线程。好处：服务停了、关机一夜，回来状态照样对，也不怕线程崩。
2. **委屈改成"分档 + 地板"模型**（2026-11-04 升级，取代原来的"留 70%"）。
   原文档写"衰减上限 70%"，字面实现会让冷战态（>65）永远退不出去，除非道歉；这不像记仇，像记一辈子。
   现在按楼主提的三档来做：
   - 小生气（15~34）：哄一句直接清零，不用道歉；
   - 中生气（35~64）：必须"道歉 + 哄"两样都出现，地板 36，少一样就停在那儿；
   - 大生气（≥65）：道歉和哄都**不动数字**，只缩短"冷静时间"（默认 6h，道歉 ×0.6、哄 ×0.8，下限 1.5h），到点才解锁。
   关键概念是**地板**：时间只能把她磨到地板，再往下要靠对应的解法。加委屈（被凶、冷落）则各档照加。
   配套：她已经在生气时，冷落按 ×0.5 打折（`neglect.angry_factor`），否则"中生气 + 4 小时不理"会一次顶满 100。
   另一个坑：中/大生气时不能再让她"哄一句就降 8 分"，否则哄几句就掉出档位，地板形同虚设——所以这两档里哄/道歉只记录、不动数字。
3. **appraisal 先走规则表，不接 LLM**。v1 一个 key 都不用、零延迟、可解释、可改配置。P2 换成一次轻量分类调用，产出结构不变。
4. **instruct 照样算出来但不硬依赖**。你手上的 MiMo / Seed-VC 只吃 speed / pitch；instruct 先带在 `plan["voice"]` 里，将来接 CosyVoice2 / EmotiVoice 时直接可用。
5. **面板画"未来 24h 预测"而不是历史曲线**。历史曲线在真实时间下几乎不动（1 秒 1 像素），看不出任何东西；预测曲线按一下按钮立刻变形，能直接看出"两小时不管她会委屈到哪一档"。
6. **她问了没得到回答，就不算话题结束**。这是 R9 的核心：`her_last_asked` 为真时 `maybe_close` 不生效，冷落值照算。
7. **冷落值封顶 80**。不封顶的话，一晚上不聊就能把 grievance 顶到 300，后面所有阈值失去意义。

## 5. 已知但故意没做

- 声音（speak）不生成，只出参数。
- 主动消息只做"该不该发"的判定，不生成文案（文档 §6.3：文案归 LLM）。
- 多人界面没做，但数据结构已经按人分好了。
- 微光小屋的 webhook 推送没实现，只确认了字段兼容（它的 `event_type` 里 `message_reply` 正好对得上，我们只加字段）。
